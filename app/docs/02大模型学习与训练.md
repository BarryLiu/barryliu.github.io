# 02 大模型学习与训练（含 ModelScope 魔搭高阶实践）

## 1. 这份文档解决什么问题

很多同学学大模型时会遇到三个痛点：

- 概念很多，但不知道先学什么、后学什么；
- 训练流程看了很多教程，自己落地时仍然容易卡住；
- 会用 API，但不会从“模型能力”角度设计训练与评测闭环。

这份文档目标是给你一条清晰路径：  
**从大模型基础认知 -> 训练方法体系 -> 工程落地流程 -> ModelScope 魔搭高阶实战**。

---

## 2. 大模型到底学什么

### 2.1 大模型的本质

大语言模型（LLM）本质上是在做：

1. 把文本映射成向量表示（Embedding）
2. 在上下文条件下预测下一个 token
3. 通过海量数据学习语言模式与任务能力

它不是“记住答案的数据库”，而是“概率建模 + 表示学习 + 条件生成”系统。

### 2.2 三层能力结构

理解 LLM，建议按三层看：

- **基础能力层**：语言理解、生成、知识压缩
- **任务能力层**：问答、分类、摘要、代码、推理
- **系统能力层**：工具调用、RAG、Agent、记忆、工作流

训练与优化，最终都是为了提升这三层中的一个或多个目标。

---

## 3. 大模型训练全景图

### 3.1 典型阶段

一个通用大模型能力构建通常分为：

1. **预训练（Pretraining）**  
   用海量通用语料学习基础语言建模能力。

2. **指令微调（SFT, Supervised Fine-Tuning）**  
   用高质量指令-回答数据，让模型更“会配合任务”。

3. **偏好对齐（Preference Alignment）**  
   通过人类偏好或 AI 偏好，让回答更符合“有用、真实、安全”。
   常见方法：RLHF、DPO、ORPO 等。

4. **领域强化（Domain Adaptation）**  
   用行业数据（医疗、金融、法务、客服）增强垂直场景表现。

### 3.2 为什么多数团队不从头预训练

从零预训练成本高（算力、数据治理、工程复杂度都高），因此业务团队更常见路线是：

- 选一个强基座模型
- 做 SFT + 对齐 + RAG
- 用评测驱动迭代

也就是：**“训练不是目的，稳定提升业务指标才是目的”**。

## 4. 必须掌握的训练方法

### 4.1 全参数微调 vs 参数高效微调（PEFT）

1. **全参数微调**
   - 优点：上限高
   - 缺点：显存占用大、训练成本高、部署版本重

2. **LoRA / QLoRA（PEFT）**
   - 优点：参数量小、训练快、适配多任务方便
   - 缺点：极复杂任务可能不如全参上限高

实践中，业务场景通常先用 LoRA/QLoRA 起步，再评估是否需要全参微调。

### 4.2 指令微调（SFT）的核心

SFT 的关键不只是“喂数据”，而是数据结构设计：

- 指令是否覆盖真实任务分布
- 回答是否可执行、可验证
- 是否包含负例和边界情况
- 是否统一格式（尤其是工具调用/结构化输出）

经验：SFT 质量常常由数据质量决定，而不是由训练时长决定。

### 4.3 偏好对齐（RLHF / DPO）

- **RLHF**：通过奖励模型 + 强化学习对齐偏好
- **DPO**：直接用偏好对样本优化，无需显式 RL 回路，工程更轻

如果团队刚起步，通常先做：

1. 高质量 SFT
2. 再上 DPO 做偏好收敛

这样比直接上复杂 RL 流程更稳。

---

## 5. 数据是训练成败的第一因素

### 5.1 数据治理四件事

1. **合法合规**：版权、隐私、敏感信息处理
2. **清洗去重**：脏数据、重复数据、低质样本清理
3. **分布均衡**：任务类型、难度、长度分布合理
4. **版本管理**：数据集可回溯、可复现实验

### 5.2 数据集划分建议

- `train`: 训练集
- `dev/val`: 调参与早停
- `test`: 最终离线评测（不参与调参）
- `challenge`: 专门放长尾和对抗样本

### 5.3 常见数据坑

- 训练集和测试集污染（信息泄露）
- 样本模板过于单一，导致模型“套模板回答”
- 标注口径不一致，造成训练目标冲突

---

## 6. 训练过程中的关键超参数

以下参数最影响结果与稳定性：

- `learning_rate`：学习率过大易发散，过小收敛慢
- `batch_size`：影响稳定性与吞吐
- `max_seq_len`：决定上下文建模能力与显存需求
- `warmup_ratio`：前期稳定训练很关键
- `weight_decay`：控制过拟合
- `gradient_accumulation_steps`：显存不足时提升等效 batch

建议：先用社区稳健配置，再做小范围网格搜索，不要一开始大范围盲调。

---

## 7. 评测体系：没有评测就没有优化

### 7.1 评测要分三层

1. **离线基准评测**：通用能力（知识、推理、代码、数学）
2. **场景任务评测**：你的真实业务任务（例如工单分类、FAQ）
3. **线上行为评测**：时延、失败率、用户反馈、转化指标

### 7.2 关键指标建议

- 准确性：Accuracy / F1 / Rouge / BLEU / Pass@k
- 对齐性：helpfulness / harmlessness / honesty
- 工程性：延迟、吞吐、成本、稳定性

### 7.3 强烈建议构建“评测回归集”

每次改模型都跑一套固定 case，覆盖：

- 历史 badcase
- 新增业务场景
- 安全合规边界

这样可以避免“某项能力提升，另一项能力悄悄退化”。

---

## 8. 推理与部署基础

### 8.1 常见优化手段

- 量化（INT8/INT4）降低显存与成本
- KV Cache 提升长对话效率
- 批处理与并发调度提升吞吐
- 流式输出改善交互体验

### 8.2 系统视角的成本模型

总成本通常由以下项共同决定：

- 模型规格（参数规模）
- 输入输出 token 数量
- QPS 与峰谷波动
- 目标时延 SLA

不要只看“模型最强”，要看“在目标成本下的综合最优”。

## 9. 基于 ModelScope（魔搭）的进阶内容

下面进入高阶实践部分，重点是“平台能力 + 工程方法”。

### 9.1 何时优先考虑 ModelScope

你会在这些场景明显受益：

- 希望快速获取中文友好的模型、数据集与社区实践
- 需要从“模型下载”升级到“训练-评测-部署”一体化流程
- 团队希望减少环境踩坑与重复脚手架工作

### 9.2 高阶能力一：模型与数据资产管理

建议把 ModelScope 当成“模型供应链”来用，而非仅下载站：

1. 明确基座模型版本（含许可证和适用场景）
2. 固定数据集版本（支持回溯）
3. 记录实验配置（超参、代码版本、数据版本）
4. 产出可复现的训练卡与评测卡

这会显著提升团队协作效率，避免“同名实验不可复现”。

### 9.3 高阶能力二：基于 ms-swift 的 SFT / LoRA 训练

在魔搭生态中，`ms-swift`（或同类官方训练工具链）常用于高效微调。

高阶实践建议：

- 首先跑通小样本端到端训练（100~1000 条）验证 pipeline
- 再逐步扩大数据规模，观察 loss 与任务指标是否一致改善
- 使用 LoRA/QLoRA 做快速迭代，多 adapter 并行实验
- 将 prompt 模板、系统指令、输出格式纳入版本管理

关键原则：**先保证“可复现与可解释”，再追求绝对分数。**

### 9.4 高阶能力三：偏好对齐（DPO）与安全对齐

在业务场景中，仅有 SFT 往往不够。建议增加：

1. 偏好对数据（chosen/rejected）
2. DPO 训练轮次
3. 安全评测集（越权、注入、违法违规、幻觉）

推荐流程：

- 先 SFT 建基础行为
- 再 DPO 调整回答偏好
- 最后做安全回归，形成上线门禁

### 9.5 高阶能力四：评测自动化（离线 + 回归）

你可以在 ModelScope 生态里构建自动评测流水线：

- 每次训练产出自动触发评测
- 固定业务数据集 + 通用 benchmark 双轨评测
- 输出可视化报表（能力雷达、版本对比、退化告警）

建议至少维护三类榜单：

1. 通用能力榜
2. 业务能力榜
3. 安全与鲁棒性榜

### 9.6 高阶能力五：模型服务化与灰度发布

训练完成并不代表可上线，建议建立：

- 多版本模型路由（A/B 或按租户分流）
- 灰度策略（小流量验证后逐步放量）
- 回滚机制（异常指标触发自动回退）
- 成本监控（token 成本、GPU 利用率、吞吐）

这一层决定了“模型能力”能否稳定转化为“业务价值”。

### 9.7 高阶能力六：RAG 与微调协同策略

很多团队会问：到底该做 RAG 还是微调？

一个可落地的决策原则：

- 知识更新频繁、事实性强：优先 RAG
- 风格与流程约束强：优先 SFT
- 复杂场景：RAG + SFT 结合

实践里通常是：

1. 先用 RAG 快速补知识
2. 再用 SFT 固化回答风格与工具调用格式
3. 用评测确认是否仍需 DPO 对齐

---

## 10. 推荐的落地路线（4 周样例）

### 第 1 周：搭建基础闭环

- 选择基座模型
- 准备小规模高质量指令数据
- 跑通一次 SFT + 离线评测 + 推理服务

### 第 2 周：提升任务效果

- 扩充数据并做分层清洗
- LoRA/QLoRA 多实验并行
- 建立业务回归集

### 第 3 周：做偏好与安全对齐

- 构建偏好对数据并尝试 DPO
- 增加安全评测与注入对抗样本
- 建立上线门禁阈值

### 第 4 周：工程化与灰度

- 多版本管理 + A/B 灰度
- 延迟/吞吐/成本优化
- 建立自动回滚与监控告警

---

## 11. 你最该避免的 8 个误区

1. 只看 benchmark，不看业务评测
2. 只训练不做误差分析
3. 忽视数据版本管理，实验无法复现
4. 追求模型参数规模，忽视时延和成本
5. 把 RAG 当万能药，忽视检索质量
6. 把微调当万能药，忽视知识更新机制
7. 没有灰度与回滚，直接全量上线
8. 不做安全回归，线上风险不可控

---

## 12. 总结：一条真正可执行的主线

如果你要把大模型做成可上线系统，建议始终围绕下面主线：

**数据治理 -> SFT/对齐 -> 评测回归 -> 服务化部署 -> 线上反馈再训练**

在这个主线里，ModelScope（魔搭）最大的价值是：  
让你从“零散工具拼装”升级为“标准化模型工程流程”，并把训练、评测、部署真正串成闭环。

只要你把“可复现、可评测、可回滚”三件事做扎实，模型能力就能稳定转化为业务价值。
