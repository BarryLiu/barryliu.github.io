# 软件开发技术术语大全设计说明

## 目标

新增一篇面向初学者和有经验开发者的软件开发通用技术知识地图。文章以“尽量完整、便于检索、可持续扩充”为目标，覆盖从计算机基础、数据结构与算法、编程语言、设计模式，到前后端、数据库、分布式系统、安全、测试、DevOps、云原生、数据工程和 AI 辅助开发的常用专业术语。

文章不把每个主题展开成教程。普通术语默认提供一句准确、独立且容易理解的描述；算法、设计模式和易混淆概念使用表格补充核心思想、适用场景、复杂度或注意事项。

## 目标读者

- 初学者可将文章作为术语词典和学习路线索引。
- 有经验的开发者可将文章作为跨领域知识地图和查漏补缺清单。
- 描述采用专业概念加通俗释义的方式，首次出现的缩写给出英文全称。

## 信息架构

文章采用从底层到上层、从理论到工程的分层结构：

1. 软件工程与研发流程。
2. 数学、计算机组成、操作系统、网络和数据表示。
3. 数据结构、算法、编程语言与编程范式。
4. GoF 23 种设计模式、扩展设计模式和架构模式。
5. API、后端、前端、移动端与跨平台开发。
6. 关系数据库、NoSQL、搜索、向量数据库、缓存和消息系统。
7. 分布式系统、系统架构、高并发、高可用和稳定性。
8. 安全、测试、代码质量、Git、构建、CI/CD 和发布工程。
9. Linux、容器、云原生、云计算、可观测性和性能优化。
10. 数据工程、主流语言与框架、UI/UX、项目协作和前沿技术。
11. 常见概念辨析和分角色学习路线。

每个一级领域使用有序章节或二级标题，领域内部允许继续拆分二至三层。最内层普通术语以紧凑的可交互术语列表展示，比较型内容使用 Markdown 表格。

## 内容范围

首版应系统收录以下重点内容：

- 常用和高级数据结构，包括链表、树、图、索引、概率型数据结构和并发数据结构。
- 排序、查找、字符串、树、图、动态规划、贪心、回溯、数论、计算几何、概率、分布式和并发算法。
- GoF 23 种设计模式逐项列出，并补充分层、六边形、整洁架构、CQRS、Event Sourcing、Saga、Outbox、Actor、Reactor、熔断等工程模式。
- 后端通用机制，包括幂等、重试、超时、限流、熔断、降级、锁、连接池、任务调度、多租户、审计和数据生命周期。
- 主流语言、框架和平台，但只解释其定位、核心机制与典型应用领域，不写安装和语法教程。
- AI 辅助开发、WebAssembly、Serverless、边缘计算、区块链、IoT、实时系统和隐私计算等前沿主题。

AI 章节聚焦软件工程相关术语，不重复现有大模型技术术语文章的详细内容。

## 交互设计

普通术语由可复用的 `TermTooltip` 组件渲染。默认只展示术语名称，减少超长文章的视觉负担；描述仍作为真实 HTML 内容存在，以兼顾可访问性和内容索引。

交互规则：

- 桌面端鼠标悬浮时显示解释。
- 键盘聚焦术语时显示解释，术语可通过 `Tab` 访问。
- 移动端点击术语时显示解释；点击其他位置、按 `Escape` 或再次点击时关闭。
- Tooltip 显示中文名、可选英文名或缩写，以及一句话描述。
- 术语使用虚线下划线或轻量荧光高亮表达可交互性。
- 提示框采用当前主题的深色背景、青色边框和有限宽度，并支持浅色主题。
- Tooltip 不遮挡整个视口，靠近屏幕边缘时应避免明显溢出。
- 关闭 JavaScript 后，术语名称和描述仍应可以通过语义化 HTML 或可访问名称获取。

不把算法复杂度、设计模式适用场景和概念辨析全部隐藏到 Tooltip 中。这些需要横向阅读的内容保留为可见表格。

## 文件与组件设计

计划涉及以下新增文件：

- `content/posts/tool/software-development-glossary.mdx`：文章 frontmatter、章节导语、算法表格、设计模式表格、辨析表格和知识地图入口。
- `src/components/TermTooltip.astro`：单个术语的语义结构与悬浮、聚焦、点击行为。
- `src/components/TermGroup.astro`：按主题渲染一组术语，避免在 MDX 中重复编写大量组件标签。
- `src/data/software-development-glossary.ts`：结构化术语数据，包括章节、分组、中文名、英文名和一句话描述。

如单个数据文件过大，可按领域拆到 `src/data/software-development-glossary/` 目录，并通过一个入口文件统一导出。是否拆分以首版实际文件长度和维护性为准，不为了形式提前拆出大量小文件。

现有 Astro 配置已经启用 `@astrojs/mdx`，内容集合 glob 也接受 `.mdx`，无需为文章格式新增集成。

## 数据模型

每个普通术语至少包含：

```ts
interface GlossaryTerm {
  name: string;
  english?: string;
  description: string;
  aliases?: string[];
}

interface GlossaryGroup {
  title: string;
  description?: string;
  terms: GlossaryTerm[];
}

interface GlossarySection {
  id: string;
  title: string;
  introduction?: string;
  groups: GlossaryGroup[];
}
```

`description` 必须是一句能够脱离上下文理解的说明，避免“见上文”“一种技术”“用于处理问题”等空泛表述。不同分组出现相同名称时，应根据语境消歧或复用统一定义。

## 内容呈现规则

- 一级知识领域使用编号标题，便于生成清晰目录。
- 二级分组提供一句范围说明，避免只堆砌名词。
- 普通术语使用 `TermGroup` 紧凑排列。
- 算法表格至少包含名称、核心思想、典型用途和复杂度或注意事项。
- GoF 设计模式表格至少包含模式、分类、意图、典型场景和常见误用。
- 概念辨析表格至少包含比较对象、核心差异、适用场景和容易混淆之处。
- 英文名称只在有助于搜索、行业识别或缩写展开时显示，避免每个中文词后机械堆叠英文。
- 产品和框架不得与抽象概念混为一类；语言与框架章节明确标记为“生态索引”。

## 可访问性与降级

- 术语触发元素必须可聚焦，并具有可识别的语义和焦点样式。
- 显示和隐藏不能只依赖颜色变化。
- 支持 `Escape` 关闭已打开的移动端 Tooltip。
- 尊重 `prefers-reduced-motion`，不添加必要性不足的动态效果。
- RSS、打印或不支持交互的环境至少保留术语名称；核心表格和章节说明始终直接可见。
- 如果 Tooltip 描述在 RSS 中无法完整呈现，文章开头应明确网页版提供交互解释，且关键知识不能仅依赖 Tooltip 才能理解。

## 性能与维护性

- 不为每个术语创建独立脚本；组件使用事件委托或纯 CSS 完成桌面端行为，只为移动端开关提供最小脚本。
- 术语数据在构建时静态渲染，不在客户端请求额外数据。
- 避免把数百个 Tooltip 同时注册为独立事件监听器。
- 描述保持一句话，避免超大 DOM 和超长浮层。
- 数据文件按确定的章节顺序维护，便于后续增补和检查重复项。

## 验证标准

实现完成后应检查：

- 文章能够被 Astro Content Collection 正确读取并生成文章路由。
- 桌面悬浮、键盘聚焦、移动点击和 `Escape` 关闭行为正常。
- Tooltip 在深色和浅色主题下可读，在窄屏和视口边缘不明显溢出。
- 算法、GoF 23 种设计模式和概念辨析内容完整。
- 页面无明显横向滚动，长表格在移动端可以安全滚动。
- `npm run test` 和 `npm run build` 可作为完整验证命令。

用户本次选择只完成正文而不运行测试和构建，因此交付时必须明确标注哪些验证未执行。交互组件属于代码改动，实际实现阶段仍应至少做静态检查；除非用户随后改变要求，不把未运行的测试描述成已通过。

## 变更边界

- 不修改当前工作区中正在编辑的 `content/posts/ailearn/llm-technology-glossary.md`。
- 不修改或恢复现有 Python 测试、`pyproject.toml`、`uv.lock` 和品牌图片变更。
- 不顺手调整无关页面、部署配置、内容迁移逻辑或主题结构。
- 如果实现中发现必须修改约定范围之外的文件，应先说明原因再扩大范围。

## 完成定义

- 形成一篇结构完整、可发布并可持续维护的软件开发技术术语知识地图。
- 普通术语均有一句话描述，并能通过 Tooltip 查看。
- 算法、23 种设计模式、后端通用机制及其他主要软件工程领域均有独立章节。
- 文章不是只有名称的目录，也不把所有内容扩写成教材。
- 最终汇报准确列出新增和修改文件、用户可见效果，以及未运行的测试和构建。
